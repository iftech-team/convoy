# 01. Фаза 1: этапы с сигналом завершения, роли, ревью → QA, «Сначала план»

Решения владельца (2026-10-14):

- находки ревью/QA уходят строителю **автоматически**, затем повторная
  проверка; **максимум 2 круга** (настраивается в проекте), дальше
  «Нужно внимание»;
- «Сначала план» — опция задачи; план **утверждает человек** по умолчанию,
  переключатель автоутверждения в задаче и проекте.

Вне фазы 1: ворктри на задачу, публикация силами Convoy, автоприём,
несколько репо (фазы 2–3).

## 1. Сигнал завершения этапа

Сейчас `queue::on_clean_exit` (convoy-core/src/queue.rs:115) и
`qa::on_exit` срабатывают только на `Exited(0)`, а интерактивные
`claude`/`codex` сами не выходят.

**Решение — файл завершения, который называет Convoy**, по образцу
`qa::verdict_file`:

| Этап | Файл | Содержимое |
|---|---|---|
| План | `<data>/stages/<run>.plan.md` | Markdown плана |
| Сборка | `<data>/stages/<run>.done.json` | `{"summary": "...", "verified": "..."}` |
| Ревью | `<data>/stages/<run>.verdict.json` | `{"verdict": "pass"\|"fail", "findings": "..."}` |
| QA | как сейчас, `qa::verdict_file` | без изменений |
| Документация | `<data>/stages/<run>.docs.json` | `{"files": ["/abs/path/…"]}` |

- Core: модуль `stage.rs` — `Stage { Plan, Build, Review, Qa }`,
  `file(stage, run_id)`, `read(stage, path) -> Option<StageResult>`;
  `on_stage_file(workspace, session_id, result)` двигает задачу (раздел 3).
- Tauri: наблюдатель (опрос раз в 2 с по активным этапам, без новых
  зависимостей) читает файл и вызывает core. После обработки сессия
  гибернируется, а не убивается — её можно открыть и продолжить.
- Бриф каждой роли заканчивается одним и тем же абзацем: «Когда закончишь,
  запиши … в `<путь>` и заверши ответ». Путь абсолютный, вне репозитория.
- Выход процесса остаётся запасным путём: `on_clean_exit`/`qa::on_exit`
  проверяют, не обработан ли этап уже по файлу (идемпотентность по
  `run_id`).

## 2. Инструкции и скиллы по ролям

**Модель** (`workspace/model.rs`):

- `Role { Plan, Build, Review, Qa, Docs }` (в фазе 2 добавится `Pr` —
  автор описания PR).
- `Project.role_instructions: Option<BTreeMap<Role, String>>` и
  `Settings.role_instructions` — глобальные значения по умолчанию.
  Миграция: существующий `review_template` (проект и глобальный) читается
  как `role_instructions[Review]`; поле остаётся для обратной совместимости
  до следующей мажорной версии.
- `Skill.roles: Option<Vec<Role>>`; `None` = только `Build` (как сейчас
  ведут себя скиллы).

**Сборка брифов**: общая функция `role_brief(workspace, project, role)`
возвращает инструкции роли (проект → глобальные → встроенные). Её
используют `planning::prepare_task`, `review::brief`, `qa::brief` и новый
`plan::brief`.

**Скиллы для сессий ревью и QA**: `review::handoff` и `qa::handoff`
заполняют `NewSession.skills` скиллами области проекта с `auto` и
подходящей ролью (сейчас — пустой список). Ограничение
`skills::MAX_ATTACHED` действует как обычно.

**UI**: «Настройки проекта → Роли»: по полю на роль (с плейсхолдером
глобального значения), «Настройки → Роли» — глобальные. В редакторе скилла
— множественный выбор ролей.

## 3. Порядок этапов и автоцикл

**Модель задачи** (`Task`):

- `round: u32` — текущий круг исправлений (0 — первая сборка);
- `stage_run: Option<String>` — `run_id` активного этапа;
- `review: Option<ReviewRun>` — по образцу `QaRun` (статус, находки,
  сессия, время);
- `TaskStatus::Attention` — «Нужно внимание» (исчерпаны круги, нет
  вердикта, этап упал).

**Проект**: `max_fix_rounds: Option<u32>` (по умолчанию 2),
`review_auto` (сейчас флаг живёт на задаче как `auto_review`; проектный
становится значением по умолчанию для новых задач).

**Переходы** (core, `pipeline.rs` — одна функция `advance(task, event)`,
JS только вызывает и рисует):

```
Сборка готова ─► проверки ─► ревью ─► QA ─► Готово к публикации (Testing, passed)
          fail ─┴────────┴────────┴─► находки строителю, round += 1
                                       round > max ─► Attention
```

- Ревью идёт **до** QA, последовательно (сейчас `main.js:4164-4171`
  запускает оба сразу).
- Fail ревью/QA: находки уходят строителю тем же механизмом, что сейчас у
  QA (`queue_feedback` / вставка в живую сессию), но **без участия
  человека**; при следующем «Сборка готова» цикл повторяется с проверок.
- Ревью без вердикта (сессия вышла, файла нет) → `Attention`, а не тихий
  проход.
- Ручные действия остаются: «Запустить QA снова», «Пропустить ревью»,
  «Отметить готовой».

## 4. «Сначала план»

**Модель**: `Task.plan_first: bool`, `Task.plan: Option<PlanRun>`
(`text`, `status: Drafting | Waiting | Approved | ChangesRequested`,
`comments`, `session_id`, `approved_at`); `Project.plan_first_default`,
`Project.plan_auto_approve`, `Task.plan_auto_approve: Option<bool>`.
Статусы задачи: `Planning`, `PlanReview`.

**Поток**:

1. Запуск задачи с `plan_first` → сессия-планировщик (агент задачи) с
   брифом: задача + спека + связанные + `role_brief(Plan)` + «Ничего не
   меняй в репозитории, не коммить. Запиши план в `<plan.md>`».
   Натив `--permission-mode plan` у Claude не используем: в нём агент не
   может записать файл, а план пришлось бы доставать из чата.
2. Файл плана → `PlanReview` (или сразу `Approved`, если автоутверждение).
3. Карточка задачи показывает план (Markdown), кнопки «Утвердить» и
   «Попросить изменения» (комментарий). Изменения → комментарий уходит в
   ту же сессию планировщика, она переписывает файл → снова `PlanReview`.
4. Утверждение → строитель стартует с `## Утверждённый план` в брифе.
   План также попадает в брифы ревьюера и QA («проверь соответствие
   плану») и хранится для описания PR (фаза 2).
5. Правка заголовка/описания задачи после утверждения сбрасывает план в
   `ChangesRequested` (как сейчас правка сбрасывает задачу в Queued).

**UI**: в форме задачи и диалоге импорта — переключатель «Сначала план»
(значение по умолчанию из проекта); колонка доски «План на утверждении».

## 5. Документация задачи

Задача считается законченной вместе с документом (у Eskhata — PDF для QA и
мобильных разработчиков, скилл `eskhata-task-doc`). Документ пишет агент, а
Convoy показывает его на странице «Документы».

**Этап «Документация»** — последний в цепочке: после зелёного QA (в фазе 2 —
после публикации, чтобы в документ попала ссылка на PR).

- Роль `Role::Docs` с инструкциями проекта (у Eskhata: «используй скилл
  `eskhata-task-doc`»), скиллы с ролью `Docs`.
- Бриф: задача, утверждённый план, итог строителя (`done.json`), находки и
  вердикты ревью/QA, ветка и PR — всё, из чего пишется документ, без
  повторного чтения истории сессий.
- Файл завершения `<run>.docs.json`: `{"files": ["/abs/path/LOYAL-523.pdf"]}`.
  Convoy проверяет, что файлы существуют и лежат в папке документов проекта.
- Проект: `docs_dir: Option<PathBuf>` — папка документов вне репозитория
  (у Eskhata `~/Desktop/EskhataDocs`); `docs_auto: bool` — запускать этап
  автоматически. Без `docs_dir` документ кладётся в данные Convoy
  (`<data>/docs/<project>/`), а не в репозиторий.
- Задача: `docs: Vec<TaskDoc { path, title, kind: Markdown | Pdf, created }>`.
- Сбой этапа не откатывает задачу: код готов, она уходит в `Attention` с
  пометкой «нет документа».

**Страница «Документы»** (`convoy-core/src/docs.rs`, `views-docs.js`):

- новый раздел «Документы задач» над файлами репозитория: по задачам
  проекта, с ключом трекера, датой и статусом задачи;
- источник — `task.docs` плюс содержимое `docs_dir` (файлы, положенные
  вручную, тоже видны);
- Markdown рендерится как сейчас; PDF — встроенным просмотрщиком веб-вью,
  кнопки «Открыть в системе» и «Показать в Finder»;
- `docs::resolve` сейчас пускает только относительные пути внутри проекта —
  для `docs_dir` нужна отдельная проверка «внутри папки документов», та же
  защита от `../`.

## 6. Eskhata: QA-скилл (вне кода Convoy)

Скилл Convoy `eskhata-qa`, область — проект Eskhata, роли `Qa` (и
`Build` — чтобы строитель проверял себя так же), `auto`. Содержание — опыт
LOYAL-523:

- `scripts/qa-up.sh` / `qa-down.sh`: админка через `php -S` с `DB_*`
  (не `artisan serve` — он не передаёт env), API как `Development` с
  локальной БД по сокету, `Outbox:Enabled=false`, Kafka на `127.0.0.1:1`,
  `Translate:UseMigrations=false`, **всегда build перед `--no-build`**;
- `scripts/api-login.py`: hello → phone → OTP → PIN для тестового номера
  (значения — из конфигов проекта, не из скилла);
- правила: никогда `es_wallet_restored`, никогда dev-Kafka-консьюмеры,
  бэкап и откат тестовых данных, не более одной попытки PIN;
- метод: A/B на одной записи (баг воспроизведён старым кодом, исчезает с
  фиксом), рестарт API из-за кэша в процессе, миграции через `--path`,
  известная ошибка `RedisObserver` при phpredis.

## 7. Тесты и проверка

- convoy-core: модульные тесты на `stage::read`, `pipeline::advance`
  (все ветки таблицы переходов, счётчик кругов, `Attention`),
  `role_brief` (проект → глобальные → встроенные, миграция
  `review_template`), выбор скиллов для ревью/QA, поток плана. Рядом с
  существующими `tests/qa.rs`.
- `cargo test -p convoy-core`, сборка Tauri-клиента, GTK-клиент
  собирается (он использует тот же core).
- Ручной прогон на тестовом проекте: задача с «Сначала план» →
  утверждение → сборка → ревью fail → автоисправление → ревью pass → QA
  pass; и задача, исчерпавшая 2 круга → `Attention`.

## 8. Порядок работ

1. `stage.rs` + наблюдатель в Tauri (без него остальное не автоматично).
2. Роли: модель, миграция `review_template`, `role_brief`, скиллы для
   ревью/QA/документации, UI настроек.
3. `pipeline.rs`: ревью → QA, вердикт ревью, автоцикл, `Attention`.
4. «Сначала план».
5. Этап «Документация» и раздел «Документы задач».
6. Скилл `eskhata-qa` и настройки проекта Eskhata (роли QA и Docs,
   `docs_dir`).
