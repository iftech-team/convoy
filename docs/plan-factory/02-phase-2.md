# 02. Фаза 2: автопилот — ворктри на задачу, очередь, публикация Convoy

Решения по умолчанию (2026-10-14, можно поменять):

- всё новое включается **в настройках проекта**; без них проект работает как
  в фазе 1;
- включение «ворктри на задачу» — это и согласие на автоматический запуск
  `setup_command` в каждой новой ворктри (для ручных сессий он по-прежнему
  подтверждается);
- параллельность больше 1 возможна только с ворктри (общий checkout не
  делится);
- публикует Convoy, только если включено «Публикует Convoy»; иначе строитель
  публикует сам, как раньше.

## 1. Ворктри и `setup_command` на задачу

- `Project.task_worktrees: Option<bool>`. Задача с режимом `pr` получает
  ворктри всегда (как и задумывалось в `queue::needs_worktree`).
- Ветка: `<branchPrefix>/<KEY>-<slug>` (`convoy/LOYAL-523-refresh-token`),
  без ключа — `convoy/task-<id8>`.
- `task_prepare` (Tauri, async): после `prepare_task` создаёт ворктри от
  `baseRef`, копирует shared paths, выполняет setup (глобальный + проекта).
  Сбой → `Attention` с текстом ошибки, ворктри остаётся.
- Планировщик работает в checkout проекта (он ничего не меняет).

## 2. Очередь с зависимостями и лимитом

- `Project.max_parallel: Option<u32>` (по умолчанию 1).
- Core `queue::next_tasks(workspace, project, running) -> Vec<id>`: занятые
  слоты — строящиеся и планируемые задачи проекта с живой сессией; берутся
  `queued` без незавершённых `depends_on`, по порядку. Без ворктри лимит = 1.
- JS `advanceQueue` спрашивает core и запускает все свободные слоты (сейчас
  берёт первую `queued`, игнорируя `depends_on`). Отметка «Готово»
  продвигает очередь — разблокирует зависимые.

## 3. Публикация силами Convoy

- `Project.convoy_publishes: Option<bool>`. Тогда бриф строителя: «закоммить
  на этой ветке, не пушь и не открывай PR — Convoy опубликует после ревью
  и QA».
- Режимы задачи: `pr` — открыть PR/MR, `describe` (новый) — только написать
  описание (для команд, где MR открывает человек), `push` — запушить ветку,
  `none` — ничего.
- Роль `Pr` — автор описания: бриф = задача, утверждённый план, итог
  строителя, вердикты ревью/QA, инструкции роли (шаблон описания проекта,
  у Eskhata — шаблон `eskhata-pr`). Файл завершения `<run>.pr.json`:
  `{"title": "...", "body": "..."}`.
- Затем Convoy (`publish.rs`, команды через `ProcessRunner`):
  `git push -u origin <branch>`, потом `gh pr create` (GitHub) или
  `glab mr create` (GitLab, в т.ч. self-hosted); CLI выбирается по хосту
  `origin` или настройкой `Project.pr_cli: auto | gh | glab`. URL из вывода →
  `task.pr_url`, статус `pr`. `describe` → `task.pr_title/pr_body`, кнопка
  «Скопировать». Сбой → `Attention`.
- Порядок: … → QA pass → публикация → документация (ссылка на PR попадает
  в документ).

## 4. Self-hosted URL PR

`patterns::PULL_REQUEST` понимает любой хост: `/pull/N` (GitHub, GHE),
`/-/merge_requests/N` (GitLab), `/pulls/N` (Gitea/Forgejo),
`/pull-requests/N` (Bitbucket). Открытие ссылки — `https` и `http`.

## 5. Тесты

Core: выбор задач очередью (зависимости, лимит, без ворктри = 1), имя ветки,
бриф строителя при публикации Convoy, этап публикации (успех, describe,
сбой → Attention), разбор URL PR разных хостов. Tauri: сборка. UI: flows.
