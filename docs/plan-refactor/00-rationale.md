# 00. Обоснование

## Что не так с текущим состоянием

Замер запущенного `Convoy-Preview-0.1.0` (AppImage, Wayland/ozone, одно окно,
одна сессия, аптайм ~6 минут):

```
217 MB  main                 125 MB  zygote        60 MB  utility (network)
189 MB  zygote                80 MB  gpu-process   60 MB  renderer
                                                   14 MB  zygote
────────────────────────────────────────────────────────────────────────
≈ 745 MB суммарного RSS на 7 процессов
```

Суммирование RSS завышает из-за shared-страниц; реально уникально ~400–500 МБ.
Всё равно это 400–500 МБ на приложение, которое по сути является менеджером
процессов с терминалом.

Плюс размер артефакта: локальная ARM64-сборка — **122 МБ** AppImage
(см. `docs/port/status.md`).

## Почему это переписывается легко

`apps/desktop` — 2698 строк, и структура необычно благоприятная:

```
UI      ~700 строк   renderer.js 393, files-ui.js 100, navigation.js 36,
                     index.html 62, style.css 112
                     → ванильный DOM, ни React, ни Vue, ни сборочного ада

Логика ~1100 строк   main.cjs 444 (из них ~250 — IPC-обвязка),
                     workspace.cjs 152, files.cjs 147, planning.cjs 125,
                     provider.cjs 67, preload.cjs 54, telemetry.cjs 50,
                     launch.cjs 41, git.cjs 38, worktree-setup.cjs 37,
                     transcripts.cjs 34, history.cjs 29,
                     repository-tools.cjs 19, accounts.cjs 17

Тесты   ~630 строк   36 тестов, из них 29 чисто логических
```

Зависимости: `node-pty`, `@xterm/xterm`, `@xterm/addon-fit`. Всё. Ни одной
тяжёлой библиотеки, которой нет аналога в Rust.

Почти вся логика — тонкие обёртки:
- `git.cjs` — `execFile('git', ...)` с очисткой env
- `launch.cjs` — сборка argv для `bash -ilc`
- `workspace.cjs` — валидация + атомарная запись JSON
- `files.cjs` — парсинг вывода `git status --porcelain=v1 -z`
- `transcripts.cjs` — чтение `.jsonl` провайдеров

Это портируется на Rust почти построчно.

## Рассмотренные альтернативы

### Tauri v2 — отклонён

Самый очевидный кандидат: UI переносится почти as-is (ванильный JS + xterm.js
остаются), бэкенд на Rust, ~10–20 МБ на диске, вдвое меньше RAM. 2–3 недели работы
вместо 7–9.

Отклонён по одной причине: **на Linux Tauri использует WebKitGTK**, и
[официальная документация Tauri](https://v2.tauri.app/develop/debug/linux-graphics/)
прямо пишет, что терминальные эмуляторы получают высокую задержку ввода и низкий
FPS в WebGL-heavy вьюхах — из-за DMABUF-рендерера и форматов буферов, которых не
даёт драйвер NVIDIA. Лечится `WEBKIT_DISABLE_DMABUF_RENDERER=1`, но ценой быстрого
пути рендеринга.

Convoy — это терминал. WebGL-рендерер xterm.js — самое горячее место приложения.
Тратить 3 недели, чтобы приземлиться ровно в тот сценарий, который документация
фреймворка называет проблемным, смысла нет.

Дополнительно: фрагментация webkit2gtk-4.1 по дистрибутивам против одного
Chromium везде у Electron. Требование «чтобы в Linux работало нормально»
Tauri выполняет хуже, чем Electron, а не лучше.

### Wails v3 (Go) — отклонён

На Linux это тот же WebKitGTK. Те же проблемы, плюс Go вместо Rust.

### Qt6 / QML — отклонён

Работает и на Windows, RAM ~100–180 МБ. Но терминальный виджет: QTermWidget —
POSIX-only и вяло поддерживается, а для Windows пришлось бы писать свой на ConPTY.
Раз Windows не в скоупе, единственное преимущество Qt перед GTK исчезает, а
интеграция с GNOME/Wayland у GTK лучше.

### iced / egui / GPUI + alacritty_terminal — отклонён

Минимальный расход (~60–120 МБ), полный контроль. Но терминальный рендер пишется
самостоятельно, а экосистема виджетов незрелая: 20 диалогов, дерево проектов,
split-diff, палитра команд — всё это на iced пишется в разы дольше, чем на GTK.
Неоправданный риск по срокам.

### Оптимизация Electron — отклонён

Можно убрать лишние zygote, подкрутить `--disable-features`, но базовые ~300 МБ
Chromium никуда не уйдут, а 122 МБ артефакта останутся.

## Выбранный вариант: GTK4 + libadwaita + VTE (Rust)

Единственный вариант, где оба требования выполняются без оговорок.

**VTE снимает терминальную подсистему целиком.** Это движок GNOME Console и
GNOME Terminal: создание PTY, fork, парсинг escape-последовательностей, скроллбек,
выделение, поиск по буферу, ligatures, URL-детект, sixel, IME — всё готовое и
вылизанное двумя десятилетиями. Для приложения, где терминал и есть продукт, это
решающий аргумент.

Побочные выигрыши:
- Выкидываются все Windows-ветки: PowerShell-обвязка в `launch.cjs`,
  `windowsExecutable()` в `provider.cjs`, `psQuote`/`EncodedCommand` в
  `telemetry.cjs`, windows-ветка в `worktree-setup.cjs`,
  case-insensitive сравнение путей в `workspace.cjs`.
- Выкидывается весь IPC-слой: `preload.cjs` целиком и ~250 строк обвязки
  `handle()` в `main.cjs`. Нет границы процессов — нечего валидировать.
- Выкидываются хаки с `ELECTRON_RUN_AS_NODE` (4 места).
- `plain()` / `stripVTControlCharacters` не нужны: VTE отдаёт уже
  отрендеренный текст без escape-последовательностей.
- Изображения в превью — `gtk::Picture` вместо base64 data URI.
- Сборка `esbuild` не нужна.

**Цена:** ~20 диалогов UI пишутся заново. Это основная работа и основной риск.
