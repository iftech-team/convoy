# 11. Риски и открытые вопросы

## Риск 1: Claude Code или Codex плохо выглядят в VTE

**Вероятность:** низкая. VTE — движок GNOME Terminal и GNOME Console,
через него ежедневно гоняют всё что угодно.

**Влияние:** критическое. Если TUI агентов ломается, весь план бессмыслен.

**Что может пойти не так:** ширина emoji и CJK, alt-screen переходы,
синхронизированный вывод (DECSET 2026), режимы мыши, bracketed paste,
поведение при быстром ресайзе.

**Митигация:** проверяется первым делом в M0, до любой другой работы.
50 строк кода, полдня. Если что-то не так — план останавливается здесь.

---

## Риск 2: объём UI недооценён

**Вероятность:** средняя. Это главный источник расхождения оценок.

**Влияние:** сроки. 20 диалогов, каждый со своими правилами доступности
кнопок, которые сейчас размазаны по `render()` и `renderPlanning()`.

**Что помогает:** libadwaita закрывает большую часть типовых форм
(`PreferencesPage`, `ActionRow`, `EntryRow`, `ComboRow`, `SwitchRow`,
`SpinRow`) — форма из пяти полей пишется десятком строк Blueprint, а не
вёрсткой с нуля.

**Митигация:** M2 даёт рабочее приложение через две недели. Дальше порт
используется как основной инструмент, и приоритеты расставляются по
реальным неудобствам, а не по списку. Если M5–M7 растянутся — не страшно,
они доделываются на живом использовании.

---

## Риск 3: `#[serde(flatten)]` и потеря неизвестных полей

**Вероятность:** высокая, если забыть.

**Влияние:** тихая потеря данных у пользователя, который переключается
между Electron-версией и портом.

**Почему это легко упустить:** в JS сохранение неизвестных полей получается
само собой через spread. В serde — наоборот, по умолчанию они отбрасываются
молча, без предупреждения.

**Митигация:** тест «schema 1 migrates without losing provider IDs or
unknown data» портируется в M1 и явно проверяет round-trip неизвестного поля.

---

## Риск 4: асинхронный `spawn_async` ломает порядок в `start()`

**Вероятность:** средняя.

**Влияние:** можно получить осиротевший процесс агента, если запись в
workspace упала между spawn и колбэком.

**Митигация:** состояние `TerminalState::Starting`, блокировка повторного
запуска, `killpg` в ветке ошибки внутри колбэка. Покрыть тестом с
подменённым `ProcessRunner`.

---

## Риск 5: снятие текста из VTE отличается от потока байтов

**Вероятность:** высокая (это факт, не риск как таковой).

**Влияние:** брифы ревью и сохранённый вывод будут содержать финальное
состояние экрана, а не всю историю перерисовок. Прогресс-бары и спиннеры
не засорят вывод — это улучшение, но поведение меняется.

**Открытый вопрос:** достаточно ли 48 000 символов финального текста для
качественного брифа ревью? Скорее да — сейчас в эти же 48 000 попадает
много мусора от перерисовок.

**Митигация:** проверить на реальном брифе в M3, при необходимости
увеличить лимит или брать больше строк скроллбека.

---

## Риск 6: детект `codex resume <uuid>` пропустит строку

**Вероятность:** низкая при скроллбеке 10 000 строк.

**Влияние:** сессия Codex не получит `providerID`, resume откроет
интерактивный выбор вместо точного возобновления.

**Митигация:** искать в начале буфера, а не только в хвосте; запоминать
факт находки. Запасной путь — читать `session_meta` из `.jsonl`
(`transcripts.rs` это уже умеет).

---

## Риск 7: libadwaita 1.5 недоступен в целевых дистрибутивах

**Вероятность:** средняя для Debian, низкая для Ubuntu/Fedora/Arch.

**Влияние:** `.deb` не соберётся для Debian 12 (libadwaita 1.2).

**Митигация:** для личного использования не важно (Arch). Если понадобится
Debian — AppImage или отказ от `adw::Dialog` в пользу `gtk::Window`.
Решать по необходимости, не закладываться заранее.

---

## Риск 8: расползание логики в обработчики сигналов

**Вероятность:** высокая. Классическая болезнь GTK-приложений.

**Влияние:** через год `convoy-gtk` содержит половину правил, и тесты
перестают что-либо гарантировать.

**Митигация:** граница крейтов. `convoy-core` не зависит от gtk — значит,
логика физически не может туда попасть по ошибке. Правило: если решение
принимается на основании данных, оно принимается в core; UI только
показывает и передаёт ввод.

## Открытые вопросы

**1. Blueprint или чистый код?**
Blueprint читабельнее для статичных форм, но добавляет
`blueprint-compiler` в зависимости сборки. Решить в M0 на примере одного
диалога. Склоняюсь к Blueprint для форм и коду для динамических списков.

**2. Оставить ли имя каталога `Convoy Desktop Preview`?**
За: совместимость, можно переключаться между версиями.
Против: «Preview» в имени для основного инструмента странно.
Решение: оставить на время параллельного существования. Переименовать
(с миграцией) только когда Electron-версия на Linux будет выключена.

**3. Application id.**
`com.iftech.convoy.linux` — чтобы D-Bus single-instance не конфликтовал
с `com.iftech.convoy.desktop`. Проверить в M2, что обе версии могут быть
запущены одновременно без драк за окно (при условии разных файлов
workspace).

**4. Нужен ли `gio::FileMonitor` вместо опроса телеметрии?**
Таймер 2 секунды работает и стоит копейки. FileMonitor элегантнее, но
добавляет состояние. Отложить.

**5. Что делать с `apps/desktop` в долгую?**
Пока — не трогать, это Windows-версия. Когда/если Windows перестанет быть
целью, Electron-превью удаляется целиком вместе с `desktop.yml` и
`desktop-release.yml`.

**6. Стоит ли сразу вынести `convoy-core` под C-ABI?**
Нет. Архитектурно подготовлено (крейт не зависит от GTK), но FFI-слой
пишется только когда появится реальный потребитель со стороны Swift.
Делать его «на всякий случай» — лишняя работа и лишние ограничения на API.

## Что проверить до начала работы

Чек-лист первого дня:

```
[ ] pacman -S vte4
[ ] cargo new + gtk4/libadwaita/vte4 собираются вместе
[ ] VTE запускает bash и показывает вывод
[ ] Claude Code в VTE: alt-screen, цвета, emoji, мышь, paste
[ ] Codex в VTE: то же
[ ] killpg убивает bash вместе с потомком
[ ] text_range_format даёт осмысленный текст
[ ] запись в pty().fd() доходит до приложения
[ ] glib::user_config_dir() == путь Electron-версии
```

Если все девять пунктов зелёные — план можно начинать.
